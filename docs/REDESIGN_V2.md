# REDESIGN v2 —— 第一性原理重设计

> 与 `REDESIGN.md`（v1）的关系：v1 的诊断基本正确（返工主因在规划、上下文信噪比低、
> LLM 选择器投票选平庸），六个杠杆里 L1 已证伪、L2 未通过判据、L4/L5/L6 部分落地。
> **v1 缺的不是杠杆，是目标函数。** 它把 FPY 当成给定的好目标，而 FPY 是定义在
> `quality_threshold: 8.0` 上的，8.0 恰好是全库 1023 章自评的中位数。
> v2 从「先修度量，再修架构」重新开始，并把 v1 仍然成立的部分吸收进来。
>
> 所有数字来自本仓库可复现的零 LLM 工具：`novel.py stats` / `novel.py compare` /
> `tools/prompt_census.py` / `tools/gate_census.py`；外部结论均给出链接。

---

## 0. 先修目标函数：当前系统在优化一个不可判定的量

### 0.1 三个事实叠在一起，结论是「现在的验收标准不成立」

1. **自评没有判别力。** 1021 章自评落在 7.4–8.7，均值 8.15，只有 6 次 `accepted=0`；
   失败书 5.64 与优质样本 8.69 同带。
2. **门槛压在中位数上。** 1023 章自评 median 恰为 **8.00**，而 `quality_threshold`
   就是 8.0，且它同时是 revise / replan / force-accept 的统一触发线。
   于是约三分之一的章**按构造**进入返工循环，返工的是噪声不是缺陷。
3. **判别器系统性偏好机器文本。** [StoryAlign (ICLR 2026)](https://arxiv.org/pdf/2605.04831)
   实测：GPT-4o / Gemini-2.5-Pro / Grok3 及各开源 RM 在 **Human–LLM 对**上的准确率
   显著低于 LLM–LLM 对——即它们倾向于judge 认为 LLM 写的比人写的好。
   所以「让写手更像人写的爆款」这个方向，**用自评做判据在原理上走不通**。

推论：`review_chapter` 的分数既不能排序质量，也不能定义合格。
它现在承担的两个职责（**返工权** + **FPY 的分母**）都是它承担不了的。

### 0.2 刚跑的一次实测：用被门槛决定的分数去评判门槛变更 = 循环论证

P4（`rework_trigger: score` vs `deterministic`）在 `tangshuting_e2e` @Ch46 分叉，
两臂各写 Ch47+，唯一配置差异 `novel.rework_trigger`。今日 `novel.py compare` 结果：

| | p4_score | p4_det |
|---|---|---|
| Ch47 / 48 / 49 自评 | 8.2 / 8.0 / 8.2 | **6.9 / 7.4 / 6.8** |
| LLM 调用 | 54（4 章） | 64（3 章） |
| LLM 分钟合计 | 85.42 | **111.53** |
| 规划占 LLM 时间 | 0.36 | **0.50** |

两个读法都要说清楚：

- **成本侧预期落空**：deterministic 臂本该更便宜（少返工），实测每章调用和时间都更高。
  n=3，且 det 臂第 3 章触发了 penalty=1.0 的路径，不足以定论，但方向与设计预期相反。
- **质量侧这张表读不出任何东西**：score 臂把章反复 revise 到 ≥8.0 才放行，
  det 臂在 6.8–7.4 就放行——**表里那 1.3 分的差，正是两臂放行规则的差本身**。
  用自评比较一次「改变自评的返工权」的实验，是循环论证。
  P4 判据里那条「匹配章 pairwise 胜率 ≥50%」才是唯一有效的一半（`tools/pairwise_ab.py`）。

这件事本身就是 v2 的立论依据：**先有可判定的验收标准，才有可比较的实验；
先有可比较的实验，才有可信的架构结论。** 顺序反了，六个杠杆全部无法结算。

### 0.3 重新定义目标：一个效率指标 + 一个质量指标，互不冒充

外部信号只有三类可得，按可获得性排序：

| 锚 | 是什么 | 成本 | 能判定什么 |
|---|---|---|---|
| **A. 确定性可判定量** | 长度带 / 对白率 / 破折号密度 / 片段率 / 跨章化石 / 场景与开场重复 / canon 矛盾 / **卡片契约兑现** | 零 LLM | 「写对了没有」 |
| **B. 人写锚** | `benchmark` 库的爆款结构 + 人工冻结的参考章 | 每 K 章一次 pairwise | 「写好了没有」 |
| **C. 真实读者** | 追读率 / 留言 | 系统外 | 最终真值 |

于是三个指标，各管一件事，**禁止交叉冒充**：

```
FPY'  (可判定首过率) = 一次通过「可判定验收集」的章占比      ← 零 LLM，不可被自评污染
CCR   (契约兑现率)   = 卡片可拍摄字段在正文中被兑现的比例    ← 零 LLM，规格精度的直接度量
WR    (锚定胜率)     = 每 K 章 pairwise 对人写/冻结参考章的胜率 ← 唯一的质量指标
```

**self-score 从此不进任何门、不进任何判据**，只作为可观测的诊断量留在日志里。
这一条比后面所有架构改动都重要：它把「优化质量」从一个不可判定问题
变成两个可判定问题（FPY'/CCR 由代码判定，WR 由外部锚判定）。

## 1. 当前 Pipeline 的核心瓶颈

### 1.1 结构性瓶颈：整条流水线是自指闭环

`writer` → `reviewer` → `arbiter` → `replan` 全部是同一模型家族、共享同一
`cacheable_prefix`、读同一份漂移中的记忆。系统内**没有任何外部信号入口**。

这正是 [自我纠错批判性综述 (2406.01297)](https://arxiv.org/pdf/2406.01297) 的结论所覆盖的情形：
无外部反馈的 intrinsic self-correction 不可靠，反馈生成本身是瓶颈。
仓库里有两处独立发现的同一现象：`cold_reader_review` 之所以必须**不带**
`cacheable_prefix`（否则它会批准漂移后的文风），`voice_baseline.md` 之所以必须**冻结**
（否则退化的文风变成"本书的文风"）。这两个补丁都是在给闭环打洞——说明洞需要开在架构层。

### 1.2 返工瓶颈：主战场在规划，触发器在噪声上

- 每本书头号返工原因都是 `replan`，占章数 **33%–68%**。
- 每章 **22.7** 次 LLM 调用，只有 **1** 次是「第一次写正文」。
- `gate_census`：644 份归档 review 的 penalty 总量只有 **0.41–0.42/章**，
  集中在 6 个门。把章压到 8.0 以下的是 raw score，**不是 penalty**。
  → 出血点是**触发器位置**，不是门的数量。

### 1.3 上下文瓶颈：规划才是预算大头，且比写手还大

`tools/prompt_census.py`，全库 14,976 次调用 / 991M prompt 字符：

| tag | 调用数 | prompt 中位 | 占总 prompt |
|---|---|---|---|
| `plan_candidate` | 2,500 | **131,872** | **33.7%** |
| `write` | 2,183 | 81,152 | 17.0% |
| `review` | 2,153 | 75,624 | 15.5% |
| `plan_review_fused` | 2,457 | 45,756 | 10.8% |
| `plan_arbitrate` | 1,268 | 55,866 | 9.2% |
| `extract` | 821 | 68,920 | 6.4% |

规划类合计 **53.8%**，写作 17.0%。**132k prompt 换 ~800 字符的计划**，
而这 800 字符还是三阶段委员会磨出来的共识泥浆。
[Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：
注意力是有限预算，每个新 token 都在消耗它——目标是「最小的高信号 token 集」。

### 1.4 选择瓶颈：每章约 10 次「投票选平庸」

策略老虎机 → 候选生成 → 预筛 → 6 轴融合评审 → 仲裁 → 正文候选择优 →
review 接受/拒绝 → 结构诊断 → 重掷。
pointwise 打分判别力低、分布压缩（实测 7.4–8.7 全带）；而
[pairwise 才更接近人类一致性](https://futureagi.com/blog/llm-as-a-judge/)。
tangshuting 200 章的单调塌缩是这条链的直接后果：

```
Ch0-20  8.49  →  Ch60-80  9.03  →  Ch100-120  7.65  →  Ch180-200  7.41
```

**22.7 调用/章买到的是一条向下的曲线。** 网文的价值在尾部，每个 LLM 选择器都在砍尾部。

### 1.5 一个此前未被单独命名的因素：文风吸引子

同一模型 + 近似常量的 prompt + 自反馈的记忆 = 输出分布随章数**收窄**。
证据是三处独立现象指向同一件事：647 份 review 里 **109 个化石短语**（`声音压得很低` 49 次）、
开场类型必须靠确定性轮值表才不重复、9.03→7.41 的单调塌缩。

**提高温度和加候选都无法对抗它**（同一分布内采样）。唯一有效的是**注入外部方差**：
人写范例、benchmark 结构、显式 forbid ledger、确定性轮值表。
这条把 v1 的 L4（范例锚定）从"锦上添花"提升为**架构必需件**。

### 1.6 冗余清单（能删就删，能合就合）

| 现有环节 | 判定 | 理由 |
|---|---|---|
| 策略老虎机（6 臂 Thompson） | **删** | 优化的是 arbiter 胜率，而 arbiter 无判别力 → 在噪声上做后验推断 |
| 候选生成 + 预筛 + 6 轴融合评审 + 仲裁 | **合为 1 次弧级规划** | 五段共识磨掉具体性；实测 P2 的成本收益成立（规划占时 0.69→0.41） |
| 逐章 pointwise 打分的**返工权** | **删** | §0.1；分数保留为诊断量 |
| `extract` 独立调用 | **并入 write** | 写手已知道自己写了什么；delta 与 prose 同一次输出 |
| `memory_compress`（231 次/100 章） | **删** | 派生状态不需要压缩 |
| 4 个上下文构建器（cacheable_prefix / writing_ / memory_ / lite_） | **合为 1 个 StoryState 投影** | 4 层预算是在管理自己造出的冗余 |
| `volume_plan_window` + `chapter_schedule_directive` | **删（升为一等公民）** | 两个补丁都在抢救被窗口化饿死的节拍表 |
| 35 门中的 advisory 门 | **删** | 无绑定修复动作 = 只产生噪声 directive |
| `force_accepted` / `quality_debt` 双台账 | **合为 1 条 event** | 两套账都在记录"门槛压中位数"的副作用 |
| telemetry 双写 | **保留但降级** | 当前 write-only；≥5 本才有消费价值 |
| 整章重写 | **保留为 <6.5 救援** | v1 的"永久移除"未被证明；底部 6% 是真坏章 |

### 1.7 真正影响质量的因素，按「可干预 × 可判定」排序

| # | 因素 | 可判定 | 现状 |
|---|---|---|---|
| 1 | **规格具体性**（卡片字段是否可拍摄） | 可（字符串/schema 校验） | 计划是共识泥浆，且**从不校验兑现** |
| 2 | **契约兑现**（正文是否落实了卡片） | 可（零 LLM） | **完全缺失** ← v2 的核心新增 |
| 3 | 上下文信噪比 | 可（字符数） | 写作 81k / 规划 132k |
| 4 | 文风健康（破折号/片段率/对白率/长度） | 可 | 已有，且是唯一有效的客观锚 |
| 5 | 结构错峰（兑现/场地/开场轮值） | 可 | 有表但常被窗口化饿死 |
| 6 | canon 一致性 | 半可（举证式） | 靠 LLM 打分，混在总分里 |
| 7 | 外部方差注入（人写范例） | 可 | `exemplar_rag_enabled: false` |
| — | **多候选 + LLM 择优** | — | **不在列**：向均值回归，砍尾部 |

## 2. 外部实践调研：采纳什么，不采纳什么

| 来源 | 关键做法 | v2 的处置 |
|---|---|---|
| [WriteHERE / HRP (2503.08275)](https://arxiv.org/abs/2503.08275) | 把写作分解为 retrieval / reasoning / composition 三类**异构**认知任务，HTN 式递归分解，规划深度自适应 | **部分采纳**：采纳「任务类型化」（检索、推理、成文分开供给上下文）；**不采纳无界递归**——网文是固定周期节拍，递归深度的边际收益低于其状态管理成本 |
| [ainovel-cli](https://github.com/voocel/ainovel-cli) | **确定性引擎按事实决策表路由**（主循环零 LLM，行为可穷举测试）；语义裁定由单次 Arbiter 完成且落盘可回放；step 级 checkpoint；**卷弧双层滚动规划**（只详细规划当前弧）；七维评审**每项必须引用原文举证** | **大量采纳**：决策表路由（替换 `pipeline.py` 的 if 森林）、双层滚动规划、**举证式评审**（把无判别力的打分换成可核查的引用） |
| [NovelForge](https://github.com/RhythmicWave/NovelForge) | Schema-first 卡片创作，AI 生成按 schema **校验**；`@DSL` 显式上下文注入；知识图谱保一致性 | **采纳** schema-first 卡片 + 硬校验（= `arc.py` 的 ChapterCard，但把校验从"建议"改成"硬约束"）；显式上下文引用 = StoryState 的字段级装配 |
| [AI_NovelGenerator](https://github.com/YILING0013/AI_NovelGenerator) / [AI-Novel-Writing-Assistant](https://github.com/ExplosiveCoderflome/AI-Novel-Writing-Assistant) | RAG 长期记忆 + 伏笔追踪 + 断点恢复 + 弧级规划 | 已具备（`retrieval.py` / `open_threads` / `checkpoint.py`），无新增 |
| Agents' Room / CogWriter（叙事理论分工、层级规划 + 并行生成） | 专家 agent 分工；并行生成 | **不采纳并行生成**（章间强依赖）；专家分工收缩为两类：canon 校验、prose 成文 |
| [StoryAlign (2605.04831)](https://arxiv.org/pdf/2605.04831) | 只有用**人写偏好对**训练的 RM 才能在 Human–LLM 对上正确排序 | **采纳其结论**：judge 必须锚在人写样本上（`benchmark` 库 + 冻结参考章），不锚在自评上 |
| [LLM-as-a-Judge 实践综述](https://futureagi.com/blog/llm-as-a-judge/) / [长文评测基准 (2606.01629)](https://arxiv.org/html/2606.01629v1) / [创作评测基准 (2507.00769)](https://arxiv.org/pdf/2507.00769) | pairwise 人类一致性高于 pointwise；pointwise 缺校准 | **采纳**：唯一的质量指标是 pairwise |
| [Rubric 生成 (RRD)](https://www.researchgate.net/publication/400506257_Rethinking_Rubric_Generation_for_Improving_LLM_Judge_and_Reward_Modeling_for_Open-ended_Tasks) / [rubric reward hacking (2606.04923)](https://arxiv.org/pdf/2606.04923) | 结构化非冗余 rubric 提升 judge；但 rubric 会被 reward-hack | **采纳 rubric，但只用于举证式核对**（可引用原文的事实项），不用于打总分——总分正是被 hack 的那个量 |
| [自我纠错综述 (2406.01297)](https://arxiv.org/pdf/2406.01297) | 无外部反馈的 intrinsic self-correction 不可靠 | **采纳**：revise 只保留有外部可判定信号的那部分（确定性门 + canon 举证） |
| [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 最小高信号 token 集；compaction；just-in-time 检索 | **采纳**：StoryState（~15k）+ JIT RAG，取代 4 个构建器与 LLM 压缩 |
| [多 agent 长故事生成 (2506.16445)](https://arxiv.org/pdf/2506.16445) | 多 agent 分工维持长程一致性 | 作为一致性方案的对照；我们用**确定性 canon 投影**而非 agent 协商实现同一目标（更便宜、可测试） |

**一句话总结外部经验：业界正在把 LLM 从「决策者」降级为「执行器」，
把决策交给确定性引擎和 schema 校验；把评价从「打分」改成「举证」和「对比」。**
v2 就是这条路线在本仓库的落地。

## 3. 新架构

### 3.1 一句话

**一条确定性流水线，四种模型调用，一个外部锚。**
确定性引擎按决策表路由（零 LLM），模型只在四个位置被叫醒：
弧级规划（奢侈，每 ~10 章一次）、写正文（唯一出货，1 次）、
举证式一致性核对（1 次 low）、定点修复（按需 ≤1 次 low）。
外部锚每 K 章一次 pairwise，不参与返工，只更新 directives 与范例池。

### 3.2 数据流

```
BRIEF (prompt.md, 不可变)  ─── bootstrap ×1 ───┐
                                               ▼
CANON = append-only 事件日志（SQLite，唯一真相源；每章追加 1 条 ChapterDelta）
   │
   │  纯函数投影（零 LLM，可缓存，字节稳定 ⇒ prompt cache 命中）
   ▼
StoryState ≈ 15k ── 唯一上下文对象
   facts 2k │ threads 1k │ arc+card 3k │ recent 1.5k │ voice 1.5k │ ledger 1k │ rag(JIT) 4k
   │
   ├─►(1) BEAT PLANNER   每 ~10 章 1 次，max reasoning
   │        输出：本弧 10 张 schema 约束的 ChapterCard + 下一弧骨架（双层滚动）
   │        │
   │        ▼  写前确定性校验（零 LLM）：schema 完整性 / canon 冲突 / 伏线超期 /
   │           场景骨架重复 / 开场类型重复 / 兑现类型三连 / 轮值表冲突
   │        │  违规 → 卡片修复（1 次 low 调用，只改被指出的字段）
   │        ▼
   ├─►(2) WRITER  **1 次调用**，输入 = StoryState + ChapterCard + RAG top-3
   │        + 本书/人写范例 ×2（对白密集 + 动作密集）+ 约束锚点（置于 prompt 末尾）
   │        输出 = prose **+ ChapterDelta**（同一次调用，取消独立 extract）
   │        │
   │        ▼  L0 确定性修复（零 LLM，keep-only-if-improved）
   │           破折号密度 / 片段行合并 / 化石轮换（仅替换表内）/ 写景开场降级
   │        ▼
   │      ┌─ 可判定验收集（零 LLM，10 项，每项必须声明修复层）──────────┐
   │      │  含 **CCC 契约兑现校验**：卡片的 where/who/关键道具是否出现，  │
   │      │  exit_hook 的具体物是否落在末 400 字                          │
   │      └──────────────────────────────────────────────────────────────┘
   │        │  L1 需要（预期 ~30%）→ 定点补丁 1 次 low 调用（永不整章重写）
   │        ▼
   ├─►(3) CANON 举证式核对  1 次 low：不打分，只回答「与 canon 有无矛盾 / 有无该收未收」
   │        **每条结论必须引用原文片段**；无引用即视为无问题（cite-or-drop）
   │        │  矛盾 → 定点改句（L1）；结构性问题 → 改**下一张**卡片（L2），不重写本章
   │        ▼
   └─►(4) CANON.append(ChapterDelta) → StoryState 失效重算（零 LLM）

每 K 章：(5) ANCHOR  pairwise（新章 vs 冻结参考章 / benchmark 结构）
         → 更新 writer directives + 范例池 + forbid ledger；**不触发返工**
```

### 3.3 模块职责（6 模块 + 2 保留，~4,200 行；现状 27,215 行 / 24 模块）

| 模块 | 行数 | 职责 | 明确不做 |
|---|---|---|---|
| `canon.py` | 450 | 事件日志；`StoryState` 纯函数投影 + 缓存；markdown 投影**仅供人读**（不回灌） | 不做 LLM 压缩、不做 4 层预算、不做记忆自反馈 |
| `beat.py` | 400 | 双层滚动节拍（当前弧详章 + 下一弧骨架）；ChapterCard schema；**写前确定性校验 + 卡片修复** | 不做候选/预筛/仲裁/老虎机 |
| `write.py` | 600 | prompt 装配（StoryState 字段级引用 + 范例锚定 + 末尾约束锚点）；单次调用出 prose + delta | 不做多候选采样、不做整章重写 |
| `accept.py` | 550 | 可判定验收集（10 项，每项 `repair=L0/L1/L2`）；**CCC 契约兑现校验**；举证式 canon 核对 | 不做 pointwise 打分、不做无修复动作的 advisory 门、**不做本章无法转绿的阻塞门**（§3.4 ④） |
| `fix.py` | 400 | L0 确定性文本变换；L1 定点补丁；全部 keep-only-if-improved | 不做整章重写（<6.5 救援路径除外，且必须显式记账） |
| `anchor.py` | 300 | 每 K 章 pairwise vs 人写锚；维护参考章、范例池、forbid ledger | 不做逐章评价、不产出返工权 |
| `run.py` | 550 | **决策表主循环**（零 LLM 路由）、step 级 checkpoint/resume、并发、CLI | 不在主循环里叫 LLM 做判断 |
| `llm.py` / `retrieval.py` | 保留 1,972 | 流式/超时/salvage/JSON 修复；无依赖 TF-IDF RAG | — |

配置键 **512 → ~40**（API 路由 15 + preset 1 + 验收集阈值 20 + 节奏 4）。
其余下沉为代码常量：**Code over Config**——不需要用户调的东西不该是旋钮。

### 3.4 四个关键机制（v2 相对 v1 的真正新增）

**① CCC 契约兑现校验（零 LLM，规格精度的闭环）**

v1 说「把规格写得可拍摄」，但从不检查写手是否照做。仓库自己的记忆条目
`doubao constraint salience` 已经记录了写手会漏契约。CCC 把它变成可判定量：

```
card.where 的地名     → 必须出现在正文
card.who 的每个人名   → 必须出现
card.turn 的关键物    → 必须出现
card.exit_hook 的具体物 → 必须出现在末 400 字
card.forbid 的每一项   → 必须不出现
CCR = 兑现项 / 总项数
```

不达标 → L1 定点补写（只补缺的那一项），而不是重写整章。
**这条同时给了「规格是否精确」的可测量反馈**：如果某类字段长期 CCR 低，
说明卡片那一栏写得不可拍摄，改的是 planner 的 schema 而不是加约束文字。

**② 举证式核对取代打分（cite-or-drop）**

借 ainovel-cli 的「每项必须引用原文举证」+ [RRD](https://www.researchgate.net/publication/400506257_Rethinking_Rubric_Generation_for_Improving_LLM_Judge_and_Reward_Modeling_for_Open-ended_Tasks) 的结构化 rubric，
但**去掉总分**（总分是被 reward-hack 的量，见 [2606.04923](https://arxiv.org/pdf/2606.04923)）。
调用只回答可核查的事实问句，且必须给出原文引用；引用无法在正文中字符串匹配的结论**自动丢弃**。
这样 LLM 的输出从"意见"变成"可被代码验证的指控"，闭环因此有了一个真实的外部约束。

**③ 阻塞门的可行动性不变量（Actionability Invariant，§8 实测后补入）**

这一条不是从外部文献来的，是本仓库 643 章语料实测出来的，而且它是**验收集能否成立的前提**：

> 一个门要有阻塞权，它测的量必须是**本次尝试可以改变**的。
> 注册一个阻塞门时必须先回答：**这一章能做什么让它变绿？** 答不出来，它只能是 advisory。

理由是对称的：§0 说自评分不可据以行动（没有判别力），
而闩锁门同样不可据以行动（有判别力，但指错了人——它惩罚的是本章无法改变的历史）。
两者造成的浪费性质相同，都是「对不可改变的量做结构性重做」。
实测三例（全书累计化石比、体裁标签冒充章型、简报里不存在的能力白名单）合计吃掉 4.0pt 首过率，
且每一次强制重掷都是**注定失败**的重掷——`chapter_mode` 被阻塞后重规划仍被阻塞的比例是 **89%**。

落到 v2 的具体约束，`accept.py` 的门注册表必须携带三个字段而不是一个：

```
repair = L0 | L1 | L2 | advisory      # 谁来修（已有）
scope  = chapter | card | book        # 测的是谁的属性
        └─ book 级的量【永不】阻塞单章；它只能变成 directive 或下一张卡片的 forbid
proof  = 该门的阈值 vs 实测分布的位置   # 注册时必须给出，防止阈值不可达（死键）
```

`scope` 直接杀死 A 类缺陷（全书累计量不得阻塞单章），
`proof` 直接杀死死键（`book_fossil_hard_ratio` 0.20 落在候选下限 0.30 之下 ⇒ 恒真；
`fingerprint_warn_threshold` 0.65 对实测最大 0.448 ⇒ 恒假，已删）。
两类缺陷在 v1 里都要靠事后回放才能发现，在 v2 里是注册时的必填项。

**④ 决策表路由（Less Agent, More Structure）**

`pipeline.py` 2,689 行的 if 森林换成一张事实表，主循环零 LLM、可穷举测试：

| 状态 | 条件（全部零 LLM 可判定） | 动作 |
|---|---|---|
| `need_arc` | `chapter_num % arc_span == 1` 或无卡片 | BEAT PLANNER |
| `card_invalid` | 写前校验有 CRITICAL | 卡片修复（≤1 次） |
| `need_draft` | 无 `chapter_current` | WRITER |
| `l0_pending` | 有草稿，未跑 L0 | L0（零 LLM） |
| `l1_pending` | 验收集有 L1 项且未用满预算 | 定点补丁 |
| `canon_pending` | 未做举证式核对 | CANON 核对 |
| `next_card_patch` | 核对给出结构性问题 | 改**下一张**卡片 |
| `rescue` | 只在 `score < 6.5`（诊断量）且以上皆已尝试 | 整章重写（显式记账） |
| `commit` | 验收集全通过或 L1 预算用尽 | append delta / 提交 |

### 3.5 为什么这提高首过率（逐条对应根因）

| 根因 | v2 的对策 | 为什么起作用 |
|---|---|---|
| 自指闭环（1.1） | 人写 pairwise 锚 + cite-or-drop + 确定性验收集 | 三个外部约束入口，都不由被评价的模型自己裁定 |
| replan 占 33–68%（1.2） | 无 replan 路径：卡片写前修，正文写后**定点**补 | 修一张坏卡 ~2k token；修一章坏正文 = write + review + 重掷 |
| 触发器压中位数（0.1） | 验收集全部可判定，self-score 无返工权 | 不再对噪声做结构性重做 |
| 规划 prompt 132k（1.3） | StoryState 15k + 弧级一次规划 | 消掉 132k × 2500 次这个最大单项 |
| 10 次投票选平庸（1.4） | 选择事件 10 → 1（仅 pairwise，且不参与逐章择优） | 不再向均值回归，保住尾部 |
| 文风吸引子（1.5） | 人写范例轮换 + forbid ledger + 确定性轮值表 | 外部方差是唯一解，温度和候选数都不是 |
| 规格不兑现（1.7 #2） | CCC | 第一次让"写对了没有"成为可判定量 |
| **闩锁门（§8 实测，4.0pt）** | `scope`/`proof` 注册字段 + 可行动性不变量 | 全书级量不得阻塞单章；阈值必须在注册时对齐实测分布，死键无法通过评审 |

## 6. 风险与反证条件

每条设计都写明「什么结果会证伪它」——没有反证条件的设计不是设计。

| 主张 | 反证条件 | 若被证伪则回退到 |
|---|---|---|
| 删多候选（N=1 + 强先验优于 N=3 + 坏选择器） | Q4 后 WR 显著下降 | N=2 + **pairwise** 择优（不回到五段委员会） |
| CCC 提高首过率 | CCR 高的章 WR 不高于 CCR 低的章 | 说明卡片字段与读者观感无关，退回只做文风门 |
| 举证式核对能替代打分 | 引用可匹配率过低（LLM 编造引用）或漏报率高于打分 | 保留打分但只作为**排序**用于 refine 优先级，仍不给返工权 |
| 人写锚可用 | pairwise judge 在「人写 vs 本书」上表现出 StoryAlign 报告的偏机器倾向，且无法用 rubric 纠正 | 改用结构化对标（benchmark 的节拍/钩子结构差异）而非文本偏好 |
| StoryState 15k 够用 | 一致性错误（canon 核对命中数）随上下文缩减上升 | 提高 rag top-k 而非恢复 4 层构建器 |
| 决策表足够表达 | 出现必须由 LLM 判断的路由分支 | 该分支单独调 Arbiter 一次并落盘（ainovel-cli 的做法），主循环仍零 LLM |
| 弧级规划优于逐章 | 卡片在弧内后段的 CCR 显著低于前段（远期规划空洞） | 缩短 `arc_span` 或改双层滚动的展开点，而非恢复委员会 |

**最大的不确定性没变，但换了位置**：v1 的不确定性是「删多候选是推断不是实验」；
v2 的不确定性是「WR 这把尺子本身尚未校准」。
后者更值得先解决——因为在尺子造好之前，v1 的那个问题**在原理上无法被回答**。

## 7. 一句话

当前系统把 ~90% 的算力用于补救，而补救的触发信号（自评 8.0）恰好压在自身分布的中位数上，
且这个信号被实测证明既无判别力、又系统性偏好机器文本。
**所以先要换的不是流水线，是尺子。**

v2 = 一把可判定的尺子（验收集 + CCC + 人写 pairwise 锚）
　　+ 一条确定性流水线（决策表路由，零 LLM 主循环）
　　+ 四次模型调用（弧规划奢侈一次、写作唯一出货、举证核对、定点修复）
　　+ 一个外部方差源（人写范例 + forbid ledger + 轮值表，对抗文风吸引子）。

省下的 20 次调用不是省钱，是把算力从「投票选平庸」搬回「写对一次」。

## 8. 执行记录 Q0.5 —— 先把「不可满足的门」拆掉（已落地，已结算）

v2 的迁移表从 Q0「先修度量」开始，但跑基线的第一件事就撞见一个不该等到 Q1 的事实：
**当前首过率的最大失分项不是模型写得不好，是三个门在惩罚模型无法改变的东西。**
这类缺陷不需要新架构，也不需要新尺子——`fpy_prime` 已经能判定它，
所以先做，单变量、可离线结算、代码只减不增。

### 8.1 判定方法：为什么必须新增 `tools/replay_gates.py`

`fpy_prime` 回放**归档 payload**，门的裁决已经烤进那些 payload 里 —— 所以
**改门的逻辑在 FPY′ 上完全看不出来**，工具会永远报告旧裁决。
`tools/replay_gates.py` 从门真正读的原始数据重算（章节正文、
归档 `plan_initial_attempt0_arbitration.json`、每本书自己的 config），
再把修正后的 payload 喂回 `_hard_block_reasons`，用同一把尺子结算。

两个先给出错误答案、然后才被这个工具排除的陷阱（细节见 LESSONS §13）：
`scene_dedupe_retry` 不是场景去重门的事件（是三门共用的 `duplicate_blocked` 标记），
以及规划门链是 `continue` 顺序链（去掉一个阻塞者必须让下游门第一次发言，否则伪造收益）。

### 8.2 三个改动（同一缺陷类：闩锁门）

| # | 门 | 闩锁在什么不可改变的量上 | 改法 |
|---|---|---|---|
| A | `book_wide_fossils` 硬拒 | 全书累计 `frac`，分子冻结、分母每章 +1（唐舒婷需再写 274 章干净章才能回到线下） | 只有本章确实用到该短语才可判硬（`in_current`）；并把 `book_fossil_hard_ratio` 抬到候选下限之上，让这个死键重新有意义 |
| B | `chapter_mode_monotony` | 体裁**标签**而非章型：`baseline="reasoning"` 下 38/41 章按构造被标成 reasoning，frac ≥ 0.93 对 0.80 阻塞线 → 永久开启 | 用无偏分类器计 frac（报告仍用有偏标签）；被阻塞后重规划仍被阻塞的比例从 89% 归零 |
| D1 | `CONTRACT_SYSTEM` 的强制 `ability_whitelist` | 简报里根本没有的能力：bootstrap 分别在契约和 bible 里编出两个互相矛盾的金手指，从 Ch1 起每章 HARD 违约 | 提示词按「简报是否真的建立了特殊能力」分支，写实题材必须留空数组 |

三者都只**收窄裁决**，不放松规避压力：化石短语照旧每次扫描进 `directives`，
章型指令照旧点名有偏标签，契约照旧逐章校验——变的只是「能不能据此拒稿」。

### 8.3 实测（643 章归档语料，`--fix` 分臂）

| 臂 | 全库 FPY′ | 备注 |
|---|---|---|
| 基线 | 526/643 = **81.8%** | 4 本 < 80% |
| 仅 A | 539/643 = 83.8% (+2.0) | tangshuting 76.4→81.9，yeban 76.9→84.6 |
| 仅 B | 537/643 = 83.5% (+1.7) | tangshuting_e2e 62.2→86.7 |
| **A+B** | 552/643 = **85.8%** (+4.0) | e2e →91.1（+28.9，超加性） |

超加性的原因是两门在拒同一批章：只修一个，那些章仍会被另一个拒掉，
所以任何单臂都测不出全部收益。**分臂用于归因，决策看合并数。**

修后逐本（≥25 章的书全部 ≥80%）：huangliang 99.0 · tunshi 98.1 · e2e 91.1 ·
yeban 84.6 · tangshuting 81.9 · v1_backup 80.5。
剩两个小样本：guize_guaitan 69.2%（n=13，4 次失分全是网关返回损坏 JSON，
不是引擎判据问题）· huangliang__ablate 75%（n=8，消融臂）。

**精度是核实过的，不是假设的**：门链存活直方图显示 11 次重规划在修后仍被阻塞
（8 `low_plan_score`、2 `chapter_mode`、1 `visual_payoff`），

D1 **不在这张表里，且无法进表**：它改的是 bootstrap 阶段的契约生成，
归档语料的契约已经写死了，任何回放都测不出它。它的收益是可推的上界

但要等下一本写实题材新书才能实测。`tests/test_latching_gates.py` 只钉住可验证的那一半：

### 8.4 两个「测了但删掉」的候选

目标里的「无效的删除」在设计阶段就执行，而不是先合并再观察：

- **正典成员化石白名单**（把 bible/characters 里的专名自动加白）：回放收益 **≤2 章（+0.3pt）**，
  且会把通用套话「有什么东西在」一起加白。否决——现有引号专名白名单已覆盖真实案例。
- **D2 容错规则**（「从 Ch1 起就违约且从未被满足过的白名单条款 → 降为 SOFT」）：
  原理正确、可离线回放，但它是给 D1 已经根治的那个情况做兜底，
  而且为一本书的证据引入一套通用的「门可自我放松」机制，正是设计原则里要避免的过度设计。否决，取根因。

### 8.5 对 v2 主线的意义

这一步没有动 §3 的架构，但改变了 §4 表里 **FPY′ 那一行的起点**：
新口径基线不是「待实测」，而是 **81.8% → 85.8%**，且失分原因已按类点名
（hard_contract 31 · style_collapse 24 · gate_rejects 20 · replanned:initial 11 ·
hard_contradictions 10）。Q1 之后要再谈首过率，就得从 85.8% 起跳。

同时它给 §0 的论点补了一个更强的版本：
**不可判定的不只是分数，还有门。** 一个门只要条件在本次尝试无法改变的量上，
它的裁决就和自评分一样不可据以行动——差别只在于自评分是没有判别力，闩锁门是有判别力但指错了人。
每加一个阻塞门，都要先回答：**这一章能做什么让它变绿？** 答不出来，就不该阻塞。

### 9.3 WR 那把尺子：本轮真正的新结论

§6 结尾写着「v2 最大的不确定性是 WR 这把尺子本身尚未校准」。本轮把它校准了，
过程中拆掉了两个错误——两个都是**先给出了看起来能用的数字**，这是本轮最值得记的部分。

**错误一：n=2 的匹配集。** 两臂只共享 2 章，两章都在交换甲乙后翻转。
`tally` 的 `interpretable=False` 报得对。修法是给 rubric 加**第二个前提**
（`anchor.PREMISE_UNMATCHED`）并按 offset 配对（`pairwise_ab --b-from`）：
五条评分标准两种前提下**逐字相同**，只有「这两段文本是什么」那一句变。
理由是那一句是 rubric 里唯一**可能为假**的部分——对位置不匹配的两臂说「同一章的两个版本」，
等于请评委去解释一个并不存在的剧情断裂，还顺便邀请它去比谁更靠近高潮。

**错误二：把「翻转过半」直接读成「评委在测位置」。** 30 对里 23 对翻转，
`interpretable=False`，我据此准备判 WR 不可测。这个推断跳步了：翻转过半有两个原因，
胜率分不开它们。**空对校准**能分开——把一章跟它自己对判，正确答案已知只能是平。
实测 deepseek-v4-pro 在两种前提下都是 **10/10 判平**，首位率 0%。
所以评委**能**判平，那 23 次翻转是这些章对它确实分不出来，按平计入是正确处置，
胜负由剩下 7 对决定：**B 6 : A 1**（符号检验单侧 p≈0.06）。不劣率 58% ≥ 50%，通过。

这条校准现在是常驻件：`anchor.null_pair_probe` + `pairwise_ab --probe N`。
它有一个不显然的实现约束——**必须按「调用」而不是按「胜方」计票**：
`judge_pair` 会把「两次都挑甲」折成 `tie`，所以一个纯位置评委在 `Verdict.winner` 上
看起来完美校准，偏好只在 `Verdict.orders` 里可见。按胜方计票的探针会给出满分并放过它。

**同时必须记下的混杂变量：章长。** A 臂均长 2480 字、18/30 低于 `chapter_min_chars`；
B 臂均长 3589 字、只有 3/30 低于。这既是 v2 的真实合规胜利（v1 后段普遍欠长本就是塌缩的一部分），
也是读者偏好评委看得见的差异。6:1 不可当作纯文风优势读。截短会破坏文本，故**标注而不消除**。

### 9.4 replay_ccc 的自伤：一个「修复冒充首稿」的新变种

改了 CCC 的**逻辑**（见 9.5），`fpy_prime` 就报不出来——它回放归档裁决。
按 `replay_gates` 的先例写了 `tools/replay_ccc.py` 从一手数据重算，第一版报 **+4 章 / 93%**。
这个数字是错的，而且错得很有教育意义：

`v2/run.py:_act_write` **每次**落 `chapter_draft.json`，而 `review_round0.json` 由
`run.round0_saved` 保护只写一次。于是任何被 rescue 过的章，归档草稿是**第二稿**，
归档裁决描述的是**第一稿**。在一份文本上重算门、再打进另一份文本的裁决里，
就是把 rescue 当成首过成功——正是那份 docstring 声称在防的陷阱，只是作用在了错的产物上。
更糟的是：丢掉首稿的章**恰好就是失败的那些**，也就是唯一有可能被修复挪动的那些。

修法不是去别处找首稿文本，而是**认清这个修复根本不需要文本**：归档 violation 里
`target` 逐字存着那条 `forbid`，`phrase` 存着命中的锚，而
`_is_misfiled_requirement(target)` 与 `phrase in _required_text(card)` 都是**卡片的纯函数**。
所以改成在裁决层重判，并调用引擎自己的那两个函数（不复制逻辑）。
首稿还活着的章（无 rescue）额外做一次文本重算**交叉校验**：24/24 一致。
真实答案是 **+2 章 / 87%**，动的恰好是 Ch219、Ch220 两章；其余 4 次失分全是 `exit_hook` 硬缺，
本修复根本不碰——这也是第一版数字该被怀疑的信号（它声称修好了我诊断为无关的章）。

### 9.5 闩锁门的第四、第五个实例（v2 侧）

CLAUDE.md 那条「加阻塞门前先答：这一章能做什么让它变绿」在 v2 上又抓到两个，都在 `forbid`：

* **Ch219（短语级）**：arc planner 把整条「…终章必须…陆时砚说'那我负责每晚关灯'…」填进了
  `forbid`，`_anchors` 从里面抬出「负责每晚关灯」当禁令，而同一张卡的 `payoff` 逐字要求这句话。
  CCR=1.0 仍被判违约。写了违约，不写违约 `payoff`——连续两章如此，跑批停住。
* **Ch220（条目级，纯型）**：整条 finale 义务被填进 `forbid`，
  「后门台阶上」被抬出当禁令。要求**只存在于那条被误填的条目里面**，没有第二个字段可比，
  所以短语级守卫看不见它（卡片 `where` 是「…后门台阶，」，与禁令差一个字）。

修法分两层：`_is_misfiled_requirement` 在挖锚**之前**判定「这条其实是义务」并整条豁免，
`_required_text` 的短语级守卫保留——后者是**裸短语**禁令（没有任何标记可读）唯一的守卫。
两层都只写 `forbid_conflicts`（带 `why`），**永不变成 writer directive**：没有哪一章能修它自己的卡片。
义务/禁止两张标记表都需要，因为「必须避免器械报告体」同时含两类标记而它是禁令，
所以禁止标记**一票否决**。方向不对称是刻意的：把禁令误判成义务只损失一行建议，
把义务误判成禁令则让这张卡片覆盖的每一章都注定首稿失败。

**上游未修**：`arc.py` 仍会把义务填进 `forbid`。门侧已经不会再冤判，但生成侧该修。

### 9.7 等位置复核：v2 重写 v1 写过的 Ch171-200（`ts_v2match`）

9.6 列的两个缺口里，「位置不匹配」这一个被这一轮关掉了：v2 重新生成
**v1 自己的章号 Ch171-200**，配对不再靠 offset。章长混杂**没有**关掉（见下）。

|---|---|---|---|
| **FPY′（归一化后）** | 26/30 = **86.7%** | 29/30 = **96.7%** | `tools/replay_gates.py` |
| 调用/章 | 25.77 | **2.50**（−90%） | `tools/window_cost.py` |
| prompt 字符/章 | 1,968,289 | **41,216**（−98%） | 同上 |
| prompt:prose | 794:1 | **12:1** | 同上 |

| **CCR** | 无（无真卡片） | **95.5%**，30/30 章通过，三个硬字段各 100% | `tools/ccr_baseline.py` |

成本一项现在是无歧义的，因为它按**时间窗**归因（`tools/window_cost.py` 读两臂各自
`llm_calls.jsonl` 的时间戳），不再拿全书 200 章的均值去比 30 章。

**FPY′ 那 −13.3pt 全是测量陈旧，不是 v1 在这一段更差。** `fpy_prime` 直接读归档裁决，
报 v1 22/30 = 73%；那 6 次失分全是 `book_wide_fossils` 硬拒，而**这个门今天在首稿上根本不可能触发**——
`review.py` 建语料时 `range(1, chapter_num + 1)` 的每一项都过 `p.exists()`，
首稿时本章还没落盘（`save_chapter` 在评审之后），所以语料是 Ch1..n-1，
每个候选的 `in_current` 恒为 False。实测 Ch185/195/200：语料 Ch1..184 → 无硬化石，
语料含本章 → 「声音压得很低」在 frac 0.41 上变硬。两臂建的是**同一个**语料
（`tests/test_latching_gates.py:BookFossilFirstDraftCorpusTest` 用源码断言钉住了这一点），
所以这条对称——它不是 v2 的优势，是 v1 归档里 6 个已修 bug 的化石。

这暴露出 `replay_gates` 自己的一个缺陷，值得单独记：它的 fix A 判据原本是
**「这条短语在本章正文里吗」**，而不是重算门。这个代理比实际的门**更严**，
于是它留下了 3 次（Ch185/195/200）现引擎产生不出来的拒绝，报 80.0% 而正确答案是 86.7%。
现在 `_live_hard_fossils` 直接用一手数据重算 `quality.book_wide_fossils`，
代理只在重算不可用时兜底（且注明兜底只可能少删、不会多删）。
**全库口径因此从 83.4% → 89.9% 订正为 83.3% → 92.0%**（`tangshuting_e2e` 62.2% → 95.6%）。

**归一化之后，两臂的写后阻塞层在这个窗口里都是零次。** v1 剩 4 次失分 = 3 次
`plan_initial_attempt` 重规划 + 1 次真实矛盾（Ch179，引文逐字在正文里，判对了）；
v2 剩 1 次 = `card_replan`。也就是说这 10pt 差距**全部来自写前的规划/卡片重试次数（3 : 1）**，
不是「v2 写出来的稿更容易过门」。这个说法比「96.7% vs 86.7%」窄得多，但它是数据支持的那一个。

**两臂的裁决词汇表不同，且缺键读作 PASS。** `hard_block_reasons` 是 `review.get(key)`，
所以一个 payload 表达不出来的桶不是「未测」而是「通过」。`v2/accept.py` 故意写 v1 的键拼法
（CCR 硬缺走 `gate_rejects`、带引文的 canon 结论走 `contract_violations`），
唯一不共享的桶是 v1 的 `contradictions`——而 v1 在这个窗口恰好在那里失了 1 分。
`fpy_prime` 现在会打印 **ENGINE MIX** 块点名这个不对称（只报告不修正：这个缺口偏向哪一臂取决于问什么）。

**WR：判据通过，但样本量是 5 不是 30。** 30 对里 25 对在交换甲乙后翻转，
而翻转的**方向**一边倒——25 个全部倒向**先读到**的那一侧，0 个倒向后读侧。
这是被测出来的位置偏好，不是「两臂难分」。9.3 写的那条推断
（「空对校准通过 ⇒ 翻转应读作分不出来」）**在这一轮被证明太宽**：
`--probe` 用同一章自比，identical text 上没有可供合理化的差别，那是最容易判平的一档；
位置偏好只在文本真的不同时才现身。方向诊断现在是常驻件
（`Verdict.flip_side` + `tally` 的 `flips_first_position`/`flips_second_position`/`flip_bias`/`n_decisive`），
报告里也会把翻转行的「理由」列标成不成立——否则那 25 行反复出现的
「乙是抒情收束、缺钩子」会被当成 v2 结尾偏弱的证据，而它只是位置合理化。
剩下的 5 对（Ch171-175）是两次都逆着位置挑了 v2，A 的决定性胜场 0。
**方向一致，量不够**：只够说「未测出 v2 更差」，不够说「v2 更好」。

**章长混杂仍在，而且比上一轮更该标注**：A 臂均长 2,479 字、18/30 低于
`chapter_min_chars`(2800)；B 臂均长 3,583 字、5/30 低于。这既是 v2 的真实合规胜利，
也是读者偏好评委看得见的差异。截短会破坏文本，故标注而不消除。

**一个 v2 侧的新缺口（不是这次能答的问题）**：`exit_hook` 是确定性硬字段，
同窗口 CCR 实测 30/30 落位——即「卡片指定的那个物件确实出现在末 400 字」。
但「物件在场」不等于「留下了未解答的问题」。真实牵引力目前**没有任何工具在测**，
`contract_fulfilment` 的 100% 不能替它作证。这是「可判定量 ≠ 读者牵引力」的缺口，
是 §0 那条纪律的下一个应用点，不是 WR 那张表能回答的。

**canon 层的灵敏度仍未证实。** `canon_check` 30/30 章都跑了，只在 1 章出结论，
而那 3 条结论全是幻觉（引的人物「汤成河」在 Ch199 出现 0 次），被 cite-or-drop 全数丢弃。
丢得对——但一个只产出幻觉、又被过滤器全接住的层，无法证明它能抓到真东西。
同窗口 v1 的 factcheck 抓到 1 个已核验的真阳性（Ch179）。**记为限制，不记为胜利。**

**CCR 的 75.1% → 95.5% 不可跨 kind 读。** 9.2 那个 75.1% 是 PROXY 卡片
（无 `turn`/`forbid`，且判据落在成稿上），目标是散文句子；95.5% 是 REAL 卡片的字段值。
这一轮建立的是**首个 REAL 基线**，不是一次 +20pt 的合规提升。

### 9.9 12 个孤儿门逐个结算（2026-07-28）

**为什么 `gate_census` 结算不了这件事，必须先造第二把尺子。** 那 12 个门里有 8 个是
advisory——advisory 的意思就是「只出 directives」，所以**没有任何东西会归档它们的判决**。
`gate_census` 读归档 `final_review.json` 的键，于是它对这 8 个门永远报「从未运行」，
而真相是「从未被测量」。这两件事在同一列数字里长得一模一样，且危险是**单向的**：
被报成静默的门会进删除清单。

`tools/orphan_gates.py` 供上 census 结构性给不了的两项测量，

### 9.10 接 `opening_route.md`：投影，而不是粘贴（2026-07-28）

§9.8 记的缺口是「v2 完全没读 `memory/opening_route.md`，`adopt-trial` 对写作侧已失效」，
CLAUDE.md 当时给的修法是「把这个文件加进 `canon.build` 的 stable 源和 `stable_key`」。
**照那个修法做会把 v1 的 prompt 膨胀缺陷原样搬进 v2**，所以实际做法多走了一步。

读 `trial.py` 的 `best_md` 才看清：这个文件是**六个块的混合物，三种不同的生命期**——

| 块 | 是什么 | 去处 |
| --- | --- | --- |
| 核心卖点 / 差异化 / 读者承诺 | 全书定位，整本书都成立 | **stable** 的 `route` 段，600 字预算 |
| 正式连载前修改指令 | 只针对开篇，连载起来就过期 | **volatile** 的 `opening` 段，500 字预算 |
| 推荐书名 / 推荐简介 | 是 `package.py` 的活 | **丢弃** |
| trial_score / variant_path | 台账 | **丢弃** |

v1 的 `memory.cacheable_prefix` 是把整个文件按 5000 字上限**整段粘贴**进每一章的 prompt，
于是一本 200 章的书把十个候选书名和五段简介运了 200 遍。
这正是 v2 存在的理由那一类缺陷，所以 `v2/canon.py` 投影它而不粘贴它。

**真正载荷的那条是拆分，不是接线。** 开篇修改指令说的是「正式连载**前**要改什么」，
它对前几章为真，之后就是一条过期指令。把它放进 stable 头会有两种死法，都很难看：
要么把一条错指令冻进缓存头，剩下 197 章每次都读；
要么让 stable 头随章号变化，**而 `stable_key` 是文件的哈希，它会继续声称头没动过**
——那恰好是这个函数存在的唯一目的所要防的失效模式。
所以 `project_opening` 在 `OPENING_ROUTE_SPAN`（3，`trial.py` 实际写的跨度）之后返回空串，
`tests/test_v2_canon.py:test_the_expiry_does_not_touch_the_cached_head` 把这条双向钉住：
Ch1 和 Ch4 的 `stable_prefix()` 必须逐字节相同，而 Ch1 和 Ch99 的 `volatile_block()` 必须不同。

反过来，`route` 段**必须**进 `stable_key`，这才是让 `adopt-trial` 中途采纳一条路线
**诚实**而不只是**有效**的地方：采纳会重写缓存头，key 随之移动，`run.py` 把 miss 打出来。
不进这个列表，前缀变了而 key 说没变——同一个失效模式的另一面。

`load()` 读文件时故意**宽松**（20000 字上限，远超两段预算之和）：
截断留给投影做。在读的时候设小上限是按**字节位置**截，
可能因为「推荐书名」那块恰好很长而把「读者承诺」切掉——为一个要丢弃的块牺牲一个要保留的块。

**测试里有一条容易漏的自欺**：`build()` 是把路线**当参数收**的，
所以一整套只测 `build` 的用例，在「引擎压根不读那个文件」的世界里也会全绿
——那恰好就是本次要修的 bug。所以另有一条 `test_load_picks_the_file_up_from_disk`
走 `canon.load`，即 `adopt-trial` 真正依赖的那条路（`conn=None` 可行，`load` 把每个 store 调用都包在 `_safe` 里）。

零 LLM 变更，`tools/fpy_prime.py` 接线前后同为 **365/438 = 83%**；测试 804 → 815 全绿。
